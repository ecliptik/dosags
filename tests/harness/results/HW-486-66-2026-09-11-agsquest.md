## Measurement method
Real hardware (vcctrl, HW-486-66), environment=realhw -- this fps/timing
datum IS a real performance number, unlike a dosbox-x/86box run.

**Independent wall-clock cross-check**: RUNMANIFEST self-reports
duration_s=433. Independently, this session's own screenshot polling
(unix timestamps, not the engine's clock) showed real in-game content
still rendering at elapsed=408s and a screen consistent with the run
having already exited (see "Known harness gap" below) by elapsed=439s --
consistent with the self-reported 433s to within the ~30s polling
granularity used. No independent bracket caught the self-report lying
about its own clock; both signals agree.

**fps context**: doskutsu's own real-hardware baseline on this same
486DX2-66 tier (HARDWARE.md) is ~25 fps -- for a different engine/game at
a lower resolution. AGS Quest at 640x360x16 is dosags's stress/coverage
workload (decision 4, PLAN.md), not the in-profile package the primary
KPI floor will be set against, so `fps_p50=9.62`/`fps_p95=10.09` here is
a first real number for the stress workload, not comparable 1:1 to that
25 fps figure or to any future in-profile-package KPI.

## Known harness gap found this run (not a dosags/AGS defect)

RUN.BAT (hand-written for this run, not yet part of the committed
harness) never restored the console to a capture-friendly video mode
after AGS.EXE exited -- same class of gap `run-dosbox.sh`/vcctrl-cell's
own finally-block mode-restore step exists to prevent (see vcctrl's
harness/vcctrl-cell "the game leaves the display in a mode the capture
stick cannot lock" comment). The engine itself finished cleanly at
tick=2632/duration_s=433 (confirmed by HW1.LOG's exit_code=0 and
AUTOPLT.LOG's full phase sequence, all `ok`) and DOS was sitting at a
perfectly normal `C:\DOSAGS>` prompt the whole time -- but vcctrl's video
capture read this as "no picture: every frame in the window was a
duplicate" continuously for ~10 more minutes, which this session initially
(reasonably, per dos-hardware-validation's "classify before escalating"
discipline) treated as a possible hang before rebooting to collect
results and discovering the run had already succeeded. **Fix for next
time**: any future dosags RUN.BAT should end with a mode-restore step
(e.g. a `MODE CO80`-equivalent, or dosags's own analogue of doskutsu's
`C:\VGACAP\MODE12`) before returning to the prompt.
