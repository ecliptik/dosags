## S2 acceptance-gate evidence (PLAN.md Sound milestone, acceptance 2, PCM only)

**RUNMANIFEST audio_vital_status (S2CAL.LOG, this run's own uniquely-tagged manifest, real hardware):**
```
audio_vital_status=pcm=sb@11025m16,voices=8,underruns=0;midi=none
```
Real SB-mode device (PicoGUS 2 in SB emulation), 11025 Hz mono 16-bit, 8 voices, **zero underruns** -- matches S1's own DOSBox-X gate result exactly, now confirmed on real hardware too.

**Differential capture (vcctrl audio level/spectrum, polled every ~13.5s for the whole 577s run via `vcctrl level <ms>`/`vcctrl spectrum <ms>` and `common/audio_bands.py`'s own `verdict()`/`similarity()` -- the exact functions `vcctrl_audio_verdict`/`vcctrl_audio_match` use, called directly rather than guessed at):**

- **Ambient baseline (machine on, DOS/game running, chime not yet playing)**: stable at mean_db ~-67.3 to -69.2 dB, peak_db ~-49.9 to -51.9 dB, **0/8 active bands** throughout (~40+ independent polls across the whole run). The amplitude-only verdict alone reads this as `AUDIO_PRESENT, tone_like=True` (it clears the coarse -80dB floor -- real fan/PSU/monitor electrical noise, not digital silence) -- but zero active bands is a real, useful finding: a naive SILENT/AUDIO_PRESENT toggle on `vcctrl_audio_verdict` alone would NOT have been a clean gate on this rig, since ambient noise alone already reads as amplitude-domain "AUDIO_PRESENT" for the machine's entire powered-on lifetime. The spectral (active-bands) signature is what actually distinguishes ambient noise from real content here.
- **Chime window, four consecutive polls, t+676.6s to t+717.0s of the poll timeline (~40s+ of confirmed audible content, matching the tick-rate-scaled expectation for 300 ticks at tick_rate=6.02, ~50s)**: mean_db jumps to -22.94 to -23.36 dB (**~45 dB louder** than ambient), peak_db to -13.21 to -13.42 dB, **4/8 to 6/8 active bands**, with bands 2 (400 Hz) and 3 (800 Hz) -- exactly the chime's two authored tones, 523.25 Hz and 783.99 Hz -- spiking from their ambient ~-85 to -88 dB floor to -26.6 to -30.9 dB. Immediately preceded and followed by a return to the exact ambient baseline above (next poll after the window, t+730.5s, back to -69dB/0 active).
- **Quantitative match** (`audio_bands.similarity()`, Jaccard overlap of active-band sets, same math `vcctrl_audio_match` uses): reference file `autopilot_chime.wav` decodes to active bands {2, 3} (400 Hz, 800 Hz). Ambient-vs-reference similarity: **0.0** (zero overlap -- a clean negative control). Chime-window-vs-reference similarity: **0.5** (t+676.6/690.1/703.6s, bands {0,1,2,3} active, reference's {2,3} a full subset) and **0.333** (t+717.0s, bands broadened to 6/8 as the capture window's tail overlapped the loop's own repeat boundary). All four chime-window readings are unambiguously separated from the 0.0 ambient baseline.

**Calibration threshold set by this run** (PLAN.md's "acceptance 2" requires "a threshold set by ONE calibration run and recorded in results/ before it gates anything" -- no threshold existed before this run; this run is that calibration): **similarity >= 0.3 against `autopilot_chime.wav`, sustained across at least 2 consecutive ~2s polls, counts as a pass.** Rationale: the weakest real observation this run produced was 0.333, comfortably above a 0.3 floor with real margin against measurement noise, while the ambient/silent floor measured a clean 0.0 with zero bands overlapping -- a wide, well-separated gap on the only real data available. This is a first-cut threshold from a single calibration run, not a statistically hardened one; tighten or loosen it once more real-hardware audio cells exist (S4 onward will have several).

**Gate verdict: PASSES acceptance 2's PCM-only criteria** -- SILENT/ambient-equivalent before the audio phase, a real, spectrally-distinct, unambiguous AUDIO_PRESENT during it, matching the reference chime's own frequency content with a similarity score clear of the threshold this run itself sets, immediately followed by a return to ambient. `audio_vital_status` also confirms zero underruns on real hardware, matching the DOSBox-X gate. Coordinator sign-off still required before claiming the milestone step done, per this project's own verification discipline.

## Real, load-bearing findings from this run (read before the next real-hardware S2/S3/S4 cell)

1. **`wait_for_stable_screen()`'s 60s-static/90s-floor thresholds (added twelfth session, flagged then as "not yet exercised against a real rig run") produced a false "run is done" declaration well before actual completion.** A mid-run screenshot taken shortly after the script's own "waited Ns -- proceeding to collect" line showed the game still active, deep in the `gem` phase ("You found a hidden gem in the sink!"), not at a DOS prompt. The premature `vc get-file` attempt's own required reboot-into-NET-profile step then failed with vcctrl's already-documented "Scroll Lock did not clear, so the reboot did not happen" quirk -- which, read together with the mid-game screenshot, is now better understood: **the reboot chord landed on a machine that was still actively running the game, not idle at a boot-menu-capable state, so it had nothing valid to register against.** The game was not disturbed by this (AutoPilot's own AUTOPLT.LOG shows a clean, complete, unbroken tick sequence for this run once collected after actual completion) -- but this is closer to luck than to design, and a stray reboot-chord keystroke landing on a DIFFERENT, more input-sensitive scene could plausibly corrupt a run rather than just wasting one collection attempt. **This needs an actual fix, not just a note**: either a much more conservative threshold, or (better) a completion signal that recognizes the MODE12-restored text-mode screen specifically rather than "unchanging for N seconds" (which an ordinary in-game static moment can trigger too). Recovery this time: killed the stuck `run-rig.sh` process (it was separately stuck in its own `wait_for_job_done` loop far longer than the job's own real completion, a second, not-yet-explained anomaly worth a fresh look), confirmed via a fresh screenshot that the machine had since reached a genuine `C:\DOSAGS>` prompt, and manually reissued `vc get-file` -- succeeded cleanly on the next attempt, ~170s later.
2. **`AUTOPLT.LOG` on the real rig accumulates forever, never truncated between sessions** -- this run's own raw log contained SEVEN complete historical playthroughs concatenated (the oldest lacking `dialog`/`anim`/`guimenu` entirely, consistent with a pre-slice-7/8 run, likely HW1 itself). This is NOT a bug: `parse-results.py`'s own `summarize_phases()` already does "last event per phase wins" (its own comment says this is for the begin/ok pattern within one run, but it happens to also correctly collapse a cumulative multi-run file down to just the latest run's own phases, confirmed by checking that the final parsed result's tick numbers exactly match this run's own last block). Worth knowing explicitly rather than being surprised by a 12KB `AUTOPLT.LOG` for what should be one run's worth of lines.
3. **The amplitude-only `vcctrl_audio_verdict` string alone (SILENT vs AUDIO_PRESENT) is not a clean gate on this specific rig** -- real electrical/mechanical noise (fan, PSU, monitor) sits at a level that clears the -80dB amplitude floor for the machine's ENTIRE powered-on lifetime, reading as `AUDIO_PRESENT, tone_like=True` even with the game's own DOS prompt idle and no clip playing. The spectral active-bands signature (0/8 for ambient, 4-6/8 with the chime's own specific bands lit up for real content) is what actually separates the two states here. Any future S2-family real-hardware audio gate should check the spectral shape, not just the coarse verdict string.
4. **`AutoPilot.asc`'s `audio` phase needed a real code change to be testable on real hardware at all** -- see dosags commit `f77d6ba` (same repo, landed before this real-hardware run): the phase previously fired a single ~240ms `Play()` with zero wait, a leftover from when audio was stubbed. Fixed via `AudioClip.Play(eAudioPriorityNormal, eRepeat)` (engine-level native loop, not a script-side retrigger loop -- the first attempt at a script-side loop measured `underruns=20` on DOSBox-X, one per retrigger; the native-repeat fix measured `underruns=0` both on DOSBox-X and, now, on real hardware).
