## Verdict

Baseline (sound-off) average fps_p50 = (4.81 + 5.17) / 2 = **4.99**.
Sound-on (OPL3) fps_p50 = **0.57**. Cost = **4.42 fps**, against the
pre-registered <= 1.5 fps bar.

**FAIL.** Not a marginal miss -- tick_rate itself collapses from ~23.8 to
~3.3 (an ~86% reduction), confirmed reproducible to the decimal place
across two independent runs, and confirmed NOT specific to the OPL3
backend (WaveBlaster shows the same ~86% collapse, 23.8 -> 3.22).

## Root cause (source-verified, not guessed)

`dos_run_tick_fixed()` (`Engine/main/game_run.cpp:1708-1762`, patch 0047)
runs up to `MAX_CATCHUP=5` extra logic-only ticks
(`skip_render_and_wait=true`) plus one normal tick per `GameTick()` call,
whenever wall-clock-expected ticks have outpaced `get_loop_counter()`.
Every one of those ticks -- catch-up or normal -- takes the
`play.fast_forward || skip_render_and_wait` branch
(`game_run.cpp:1514-1529`), which calls `audio_core_entry_poll()`
(`Engine/media/audio/audio_core.cpp:190-214`) explicitly so a
fast-forwarded or catch-up tick's own audio still gets serviced. That
function polls every active `AudioPlayer` slot (the MIDI slot included,
once music is playing) and calls `dos_audio_mixer_pump()` once per call.

On this hardware, even the sound-off arm only reaches ~23.8 ticks/s
against a 40Hz target -- backlog never clears, so **every** `GameTick()`
call runs the full `MAX_CATCHUP` burst: `audio_core_entry_poll()` fires
up to 6x per outer iteration instead of the ~1x/iteration cost profile
S0's own design (patches 0046-0048, landed before any audio milestone
existed) was validated against. With no audio device open, that 6x
multiplier is applied to a near-zero per-call cost (an empty slots list)
-- invisible. With a MIDI slot genuinely active, it multiplies a real
per-call audio-service cost by up to 6x, which pushes `tick_rate` down
further, which keeps the backlog (and thus the 6x multiplier) permanently
maxed -- a sustained, not transient, interaction. This is why the
regression reproduces exactly (same multiplier, same steady state) rather
than varying run to run, and why it hits OPL3 and WaveBlaster equally
(the multiplier applies to whatever `audio_core_entry_poll()` costs with
*any* active MIDI backend, not to OPL3-specific register I/O).

**This is a genuine interaction between two independently-shipped,
independently-validated features (S0's fixed timestep, S1/S3/S5's audio
backends) that had never been exercised together at a sustained
catch-up-heavy tick rate on real hardware before this ABBA** -- AGS
Quest's own S4MIDI1/S5WB/GUSQ2 real-hardware runs did not have
`DOSAGS_FIXED_TIMESTEP=1` set (their own `tick_rate` values, ~5.9-6.5,
match the flag-OFF baseline documented in S0's own HW11A confirmation),
so this exact combination was never measured until now.
